## Bug: Redundant network call causes avoidable failure in video acquisition

**Symptom:** Pipeline run failed at "Step 2/5: Computing audio fingerprint" with:
`SSLError: [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol`

**Where:** `get_or_create_video_record()` in `orchestrator.py` (line ~58) calls
`self.media.get_metadata(url)` → `get_light_metadata()` in `audio/downloader.py`
(line ~90), which makes its own `ydl.extract_info(url, download=False)` call to
the source site.

**Root cause:** This is a *second, independent* network round-trip to the same
site, made immediately after `download_audio_only()` already succeeded (997MB
downloaded cleanly in 2:45 — confirmed network/yt-dlp are fine). The SSL EOF
error is a transient failure (antivirus HTTPS interception or a flaky
handshake — confirmed non-structural via DNS/CLI testing in this session), but
it only had the chance to strike because of this avoidable extra call. The
video's info dict (duration, fps, width, height, codecs) is already returned
by the `extract_info(download=True)` call inside `download_audio_only()` —
`get_light_metadata()` re-fetches data that's already in hand.

**Fix:** Merge the download and metadata extraction into a single
`extract_info()` call. Have `download_audio_only()` (or a new
`download_audio_only_with_metadata()`) capture and return the `info` dict from
its own `download=True` call, and have `get_or_create_video_record()` consume
that instead of calling `get_light_metadata()` separately. This removes one
full network dependency from the critical path — not just faster, but
structurally removes a failure point (download-succeeds-but-metadata-fails
becomes impossible).

**Secondary/defensive fix (independent of the above):** Wrap all yt-dlp
network calls (`download_audio_only`, `download_video`, and — until merged —
`get_light_metadata`) in a retry-with-backoff (e.g. 3 attempts, exponential
backoff) around `yt_dlp.utils.DownloadError` / `SSLError`. This session hit
transient SSL/connection errors twice on otherwise-healthy network/DNS/yt-dlp
setup (confirmed via `Resolve-DnsName`, `yt-dlp -v` direct CLI test succeeding);
both would likely have been absorbed by a retry.

THE MAIN FIX THAT CLAUDE SUGGESTED WAS: The main fix: stop thinking in "audio frames"
You're trying to build a 1:1 mapping between video frames and audio frames. That's not how ASR (automatic speech recognition) works, and it's not necessary.
Modern ASR models (Whisper, WhisperX, Deepgram, etc.) don't take "audio frames" as input in a way that maps to video frames — they take a continuous audio stream and output text with timestamps (segment-level, and with word-level timestamp models, per-word timestamps). That timestamp is a continuous float (seconds), not a frame index.
